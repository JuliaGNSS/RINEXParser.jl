API reference

RINEXParser.BeiDouEphemeris — Type
BeiDouEphemeris(; kwargs...)

One BeiDou D1/D2 broadcast ephemeris in the units RINEX expects (angles in radians, sqrt_a in √m, times in seconds of BDT week). Field names follow the RINEX 3.05 BDS navigation record (Table A14).

aode and aodc are the age of the ephemeris and of the clock data, and sath1 is the autonomous satellite health flag (0 healthy). tgd1_b1_b3 and tgd2_b2_b3 are the two broadcast group delays in seconds.

Unlike Galileo, whose week RINEX aligns with the GPS week, toc, toe, week and transmission_time of a BDS record are in BeiDou time: week is the continuous BDT week counted from the BDT epoch (2006-01-01) - the broadcast 13-bit week plus 8192 per roll-over - and the seconds of week are BDT seconds, 14 s behind GPS time.

transmission_time refers to week, as navigation_times gives it; the spec's encoding of one that is not known is 0.999999999999e9.

RINEXParser.GalileoEphemeris — Type
GalileoEphemeris(; kwargs...)

One Galileo I/NAV or F/NAV broadcast ephemeris in the units RINEX expects (angles in radians, sqrt_a in √m, times in seconds of Galileo week). Field names follow the RINEX 3.05 Galileo navigation record (Table A8).

data_sources encodes the navigation message source and clock reference (bit field, Table A8) and sv_health packs the per-signal validity and health bits; both are assembled by galileo_data_sources and galileo_sv_health. The default data_sources = 513 is an I/NAV message from E1-B with E5b/E1 clock parameters. sisa is the signal-in-space accuracy in meters, and bgd_e5a_e1/bgd_e5b_e1 are the broadcast group delays in seconds.

week follows the RINEX convention of a continuous week number aligned with the GPS week, which is the 12-bit GST week of the navigation message plus 1024 (the Galileo epoch falls into GPS week 1024).

RINEXParser.IonosphericCorrection — Type
IonosphericCorrection(type, parameters; time_mark = nothing, sv_id = nothing)

Ionospheric correction header record, e.g. Klobuchar parameters as IonosphericCorrection("GPSA", (α0, α1, α2, α3)) and IonosphericCorrection("GPSB", (β0, β1, β2, β3)). type is one of the correction types of RINEX 3.05 Table A5: "GAL", "GPSA", "GPSB", "QZSA", "QZSB", "BDSA", "BDSB", "IRNA" or "IRNB".

Galileo's NeQuick record carries three coefficients, (ai0, ai1, ai2), and its fourth field is a spare written blank. A fourth value of zero, passed for that spare, is accepted and dropped.

time_mark and sv_id say when the parameters were transmitted and by which satellite. The mark is the hour of the day of the transmission time as a letter, 'A' for 00h-01h through 'X' for 23h-24h. RINEX 3.05 Table A5 makes both mandatory for BDS - a constellation broadcasting several sets a day, whose readers need to tell them apart - and optional elsewhere, so a "BDSA" or "BDSB" record without them is rejected.

RINEXParser.LeapSeconds — Type
LeapSeconds(count; future_count = nothing, week = nothing, day = nothing,
            time_system = "")

The LEAP SECONDS header record. count is the current number of leap seconds; future_count (ΔtLSF), week (WN_LSF) and day (DN) describe the leap-second event the message announces, which some parsers require.

time_system is what the week and day count in: "GPS" (weeks from 1980-01-06, days 1-7) or "BDT" (weeks from 2006-01-01, days 0-6). The default "" leaves the field blank, which a reader takes as "GPS".

A header also takes a plain Int or an NTuple{4,Int}: leap_seconds = 18 or leap_seconds = (18, 18, 2185, 7).

RINEXParser.ObsEpoch — Type
ObsEpoch(time, satellites; fractional_second = 0.0, flag = 0, clock_offset = nothing)

One observation epoch. time is the epoch in the file's time system (epoch_time gives it); fractional_second carries the sub-millisecond part DateTime cannot, so it is below a millisecond in magnitude. clock_offset is the optional receiver clock offset in seconds.

flag is 0 for an ordinary epoch and 1 for a power failure since the previous one. The event records of flags 2-5 (Table A3) are not written.

source
RINEXParser.ObsValue — Type
ObsValue(value; lli = nothing, ssi = nothing)

A single observation: the measurement value plus the optional loss-of-lock indicator lli and signal-strength indicator ssi. Units follow RINEX conventions: pseudorange in meters, carrier phase in cycles, Doppler in Hz, signal strength in dB-Hz.

The loss-of-lock indicator is a bit field of three bits, so it holds 0-7 (section 6.7.1); loss_of_lock_indicator sets its bits by name. The signal strength is documented as 1-9, and ssi = 0 is accepted next to those: it is what a receiver reports for a projected signal strength it does not have yet. signal_strength_indicator derives it from a C/N₀ in dB-Hz.

A non-finite value is written as a blank field, which is how RINEX records that an observation code carries no measurement for a satellite.

RINEXParser.PhaseShift — Type
PhaseShift(system, code, correction; satellites = Int[])

One SYS / PHASE SHIFT header record: the correction in cycles that was applied to the carrier phase code of system to align it with the reference signal of its band (RINEX 3.05 Table A23). satellites names the satellite numbers the correction applies to; an empty list means every satellite of the system, which is the usual case.

The record has three readings (section 5.2.12):

  • a correction (-0.25): this was added to align the phase,
  • zero: the phase arrived aligned (from the receiver, or a stream such as RTCM-MSM) and nothing was applied,
  • blank: the code needed no correction, being the reference of its band or aligned to it with "None". A code no PhaseShift names is written so.

So a header has to name every phase code Table A23 aligns with a correction other than zero, and the writer rejects one that does not. The correction is phase_correction for a receiver that applied the ICD value; where that is nothing but the table requires the phase aligned, state the one the receiver or converter applied. The codes the table states no alignment for need no shift.

PhaseShift('E', "L1C", phase_correction('E', "L1C"))  # +0.5 was applied

A reference signal takes no correction other than zero. A shift limited to satellites leaves the others of the system reading as zero.

RINEXParser.RinexDirectory — Type
RinexDirectory(directory; session = nothing, overwrite = false, kwargs...)

A writer target that names its file by the long filename convention (RINEX 3.05 appendix A1) in directory, from what the file holds when it is closed rather than from what is known when it is opened:

RinexObsWriter(RinexDirectory("/data"; country = "DEU", period = Day(1)), header) do writer
    write_epoch!(writer, epoch)
end
# /data/ROOF00DEU_R_20200010000_01D_01S_GO.rnx

The writer streams into a temporary file in directory and renames it to its rinex_filename on close. An observation file takes its start time from its header's time_of_first_obs, which the first epoch fills in.

A navigation header carries neither a time nor a marker name, so a navigation file is named after session, the RinexObsWriter of the same session: its start time is that writer's first epoch, and its site is that writer's marker name, as they are when the navigation writer closes.

obs = RinexObsWriter(RinexDirectory("/data"), obs_header)
nav = RinexNavWriter(RinexDirectory("/data"; session = obs), nav_header)

Without a session, or with one that got no epoch, a navigation file starts at the toc of the first ephemeris it wrote.

kwargs are the keywords of RinexFileName for the fields the header does not determine - monument, receiver, country, data_source, period, marker_name and start_time - and are checked when the writer is created. The file is written uncompressed RINEX, so format and compression cannot be given.

An existing file of the name is replaced only with overwrite = true. Otherwise, or if the move fails, the file stays at its temporary path with a warning, and close does not throw; file_path says where it ended up. A file that cannot be named because it has no record and no start time is removed.

source
RINEXParser.RinexFileName — Type
RinexFileName(header::RinexObsHeader, start_time = header.time_of_first_obs; kwargs...)

The name of the observation file header describes. The site fields come from the header's marker name (see site_fields), the data type from the constellations of its obs_codes - a single one names its constellation, several name a mixed file - and the data frequency from its interval. start_time defaults to the header's time_of_first_obs, which a lazily written header may not carry yet.

Any of the fields the header does not determine can be given as a keyword, as can marker_name to derive the site from another name; system and file_type cannot. A site field given as nothing is the one the marker name gives.

rinex_filename(header, start_time; country = "DEU", period = Day(1))
source
RINEXParser.RinexFileName — Type
RinexFileName(header::RinexNavHeader, start_time; kwargs...)

The name of the navigation file header describes: MN for a mixed navigation file, or the constellation of its satellite_system if it is pinned to one. A navigation header carries neither a marker name nor a time, so start_time is required and the site fields default to the station UNKN of an unknown marker; pass marker_name (the marker name of the observation file of the same session) or the site fields themselves to name the site:

rinex_filename(nav_header, start_time; marker_name = obs_header.marker_name)

As for an observation file, system and file_type cannot be given (pin the header's satellite_system instead), and a site field given as nothing is the one the marker name gives.

RINEXParser.RinexFileName — Type
RinexFileName(; station, start_time, kwargs...)
RinexFileName(name::AbstractString)
RinexFileName(header, start_time; kwargs...)

A RINEX long filename (RINEX 3.05 appendix A1), the naming convention of RINEX 3.02 and later:

ALGO00CAN_R_20121601000_01D_30S_MO.rnx

The fields are

  • station, monument, receiver, country: the nine-character site identification XXXXMRCCC - the four-character station name, the monument and receiver number 0-9 at that site, and the ISO 3166-1 alpha-3 country or region code. A country of nothing is the "XXX" of a country that is not known.
  • data_source: 'R' for a file written from receiver data, 'S' for one written from a data stream, 'U' if that is unknown.
  • start_time: the nominal start time of the first record, in the time system of the file. The field holds the day of year and the hour and minute of the day and has no seconds, so the start time is kept floored to the minute - the record says no more than the name does.
  • period: the intended collection period as a Dates.Period - Day(1), Hour(1), Minute(15), Year(1), or any sum of periods of a fixed length - or nothing for the 00U of a period that is not specified. It is kept as the single period its field holds, Day(1) + Hour(12) as the Hour(36) the name says.
  • interval: the sampling interval in seconds, written as the data frequency (30S, 01S, 05M, 05Z for 5 Hz, 01C for 100 Hz), or nothing for 00U. Navigation file names have no such field and require nothing.
  • system, file_type: the two characters of the data type, e.g. 'G' and 'O' for GO (GPS observation), 'M' and 'N' for MN (mixed navigation). system is a constellation character or 'M' for a mixed file; file_type is 'O', 'N' or 'M' (meteorological), the file type of the RINEX VERSION / TYPE record.
  • format: "rnx" for RINEX, "crx" for Hatanaka compressed RINEX.
  • compression: "gz", "bz2", "zip", or nothing for a file that is not compressed.

Construction validates every field against its fixed-width representation, so rendering a constructed name does not require further validation.

print and string render the name, so it goes straight into a path:

joinpath(directory, string(name))

The forms taking a RinexObsHeader or RinexNavHeader fill the fields the header knows - the site from its marker name, the data type from its constellations, the data frequency from its interval - so that a writer does not have to assemble a name of its own; see rinex_filename. A name is read back with parse(RinexFileName, name).

RINEXParser.RinexNavHeader — Type
RinexNavHeader(; kwargs...)

Header of a RINEX 3.05 navigation file. The corrections and leap seconds are decoded from the navigation message, so they may become available only after the writer is created. set_header! completes or replaces it any time before the first write_ephemeris! call writes it out, and add_header_records! collects them from decoded navigation messages.

satellite_system is the system character of a single-constellation file (e.g. 'G'); leave it as nothing for a mixed navigation file that may carry ephemerides of several constellations.

source
RINEXParser.RinexNavWriter — Type
RinexNavWriter(target, header::RinexNavHeader = RinexNavHeader(); overflow = :throw)

Streaming writer for a RINEX 3.05 navigation file. target is a path, an IO, or a RinexDirectory that names the file by the long filename convention when it is closed. The header is written lazily on the first write_ephemeris!, and set_header! replaces it until then. An ephemeris whose contents, but for the transmission time (and for BeiDou the ages of data), match a written record is skipped, so it is safe to forward every decoded subframe. Close the writer (or use the do-block form) to flush the file.

overflow says what becomes of an ephemeris with a value that does not fit its E19.12 field or is not finite, for which a navigation record has no blank encoding. :throw rejects it with an ArgumentError; :skip leaves the record out, makes write_ephemeris! return false, and warns once per record. A record is checked whole before any of it is written, so a rejected one leaves the file as it was.

source
RINEXParser.RinexObsHeader — Type
RinexObsHeader(; obs_codes, kwargs...)

Header of a RINEX 3.05 observation file.

obs_codes maps each satellite system character to the ordered list of observation codes (RINEX table A2, e.g. "C1C", "L1C", "D1C", "S1C") the file carries for that system. It is given as a vector of pairs to keep the system order deterministic:

obs_codes = ['G' => ["C1C", "L1C", "D1C", "S1C"]]

phase_shifts carries the PhaseShift records of the carrier phases that were aligned with the reference signal of their band; see PhaseShift for which codes need one.

signal_strength_unit is the unit of the S observations, written to the optional SIGNAL STRENGTH UNIT record; "DBHZ" is the one RINEX 3.05 defines. Left as nothing, the record is omitted and the unit is receiver-dependent as far as a reader knows.

clock_offset_applied is the optional RCV CLOCK OFFS APPL record: whether the epochs, code and phase were corrected by the receiver clock offset. Left as nothing, the record is omitted, which a reader takes as false, and an epoch reporting a clock_offset is rejected, as the format requires the record for it.

glonass_slots lists the frequency channel number (-7 to +6) of each GLONASS slot as slot => channel, for the mandatory GLONASS SLOT / FRQ # record; a GLONASS satellite that has observations in an epoch has to be in the list, or a reader cannot reconstruct its carrier frequency. glonass_code_phase_biases are the code-phase biases in meters of C1C, C1P, C2C and C2P for the mandatory GLONASS COD/PHS/BIS record: zeros for data that is aligned, and nothing, the default, for biases that are not known, which writes the record blank.

time_of_first_obs may be left as nothing; it is then taken from the first epoch passed to write_epoch! and assigned to the header, so that rinex_filename can name the file from the header afterwards.

The writer only reads the header when it writes it out on the first epoch, so fields that the data provides late - a position solution, the leap seconds decoded from the navigation message - can be completed any time before that with set_header!:

set_header!(writer; approx_position = position, leap_seconds = leap_seconds)
source
RINEXParser.RinexObsWriter — Type
RinexObsWriter(target, header::RinexObsHeader; overflow = :throw)

Streaming writer for a RINEX 3.05 observation file. target is a path, an IO, or a RinexDirectory that names the file by the long filename convention when it is closed. The header is written lazily on the first write_epoch!, so time_of_first_obs can be filled in from the data, and the header can be completed or replaced with set_header! until then. Close the writer (or use the do-block form) to flush the file.

RinexObsWriter("data.obs", header) do writer
    write_epoch!(writer, epoch)
end

overflow says what becomes of an observation value or receiver clock offset too wide for its field. :throw rejects the epoch with an ArgumentError; :blank writes the field blank, as a measurement that is not available, and warns once per observation code of a system. An epoch is checked whole before any of it is written, so a rejected one leaves the file as it was.

source
RINEXParser.SatObs — Type
SatObs(system, prn, observations)
SatObs(header, system, prn, "C1C" => value, "L1C" => value, ...)

Observations of one satellite in one epoch.

The first form takes the observations aligned with the header's obs_codes list for system, using nothing for observation codes without a measurement. The second form addresses them by observation code instead and derives the alignment from header (a RinexObsHeader or a RinexObsWriter), which cannot be misaligned:

SatObs(writer, 'G', 2, "C1C" => 21234567.890, "L1C" => ObsValue(111583948.752; ssi = 7))

A value is a plain number, an ObsValue carrying the loss-of-lock and signal-strength indicators, or nothing for a measurement that is not available in this epoch. Observation codes the header declares but the call does not mention are left blank. Codes may also be given as symbols (:C1C), and as any iterable of pairs instead of separate arguments.

RINEXParser.add_header_records! — Function
add_header_records!(header::RinexNavHeader, decoder; week = nothing) -> header

Add the navigation-header records a GNSSDecoder GNSSDecoderState has decoded to header: the ionospheric corrections (Klobuchar for GPS and BDS, NeQuick for Galileo), the time-system corrections (each constellation's offset to UTC, and Galileo's to GPS time) and the leap seconds. Available with using GNSSDecoder.

These are broadcast far less often than the ephemerides - GPS sends them once every 12.5 minutes - so a writer collects them from every decoder until the header is written:

header = RinexNavHeader(; satellite_system)
foreach(decoder -> add_header_records!(header, decoder; week), decoders)
header_written(writer) || set_header!(writer, header)

A record replaces one of the same type - for BDS, of the same type, time mark and satellite - so the latest broadcast is the one written. Of the leap seconds, the record counted in GPS time is kept over BDS's, which counts BDT, and a record announcing the next leap-second event over one that does not, as some parsers require it.

week is the one rinex_ephemeris takes. The reference weeks that are broadcast truncated - the 8-bit UTC and leap-second weeks, Galileo's 6-bit GGTO week - are resolved against it into the continuous week a header record carries, aligned with the GPS week for Galileo.

RINEXParser.epoch_time — Method
epoch_time(time_system; week, time_of_week) -> (; time, fractional_second)

The time and fractional_second of an ObsEpoch at week and time_of_week [s] of time_system: "GPS", "GAL" or "BDT", the time_system of the file, or with using GNSSSignals its GNSSSignals time system, GPST(), GST() or BDT(). week is on that time system's own count (the GPS, GST or BDT week), and the calendar time is in time_system: a BDT epoch reads 14 s behind the GPS one of the same instant.

t = epoch_time("GPS"; week = 2124, time_of_week = 345600.25)
ObsEpoch(t.time, satellites; t.fractional_second)

A negative time_of_week lies in the week before, one past the end of the week in the week after. Both parts keep the precision of time_of_week.

file_path(writer) -> Union{Nothing,String}

The path of the file writer - a RinexObsWriter or RinexNavWriter - writes: the path it was created with, or for a RinexDirectory its temporary path until it is closed and its long filename after. nothing for a writer to an IO, and for a writer to a directory that wrote no record and so left no file.

RINEXParser.galileo_data_sources — Method
galileo_data_sources(; inav_e1b = false, fnav_e5a = false, inav_e5b = false) -> Int

The data_sources bit field of a GalileoEphemeris (RINEX 3.05 Table A8), assembled from the navigation messages the record was decoded from.

A record comes from one message type, and its clock parameters, toc and sisa are the ones that message broadcasts (section 5.4.3): F/NAV carries the E5a/E1 clock and I/NAV the E5b/E1 clock, so the clock bits (8 and 9) follow from the source and are set here. A receiver decoding both messages writes one record of each:

galileo_data_sources(; inav_e1b = true)  # 513, I/NAV
galileo_data_sources(; fnav_e5a = true)  # 258, F/NAV

An I/NAV record merged from both of its carriers sets inav_e1b and inav_e5b together. A source mixing F/NAV and I/NAV is rejected.

galileo_sv_health(; e1b_dvs = 0, e1b_hs = 0, e5a_dvs = 0, e5a_hs = 0,

RINEXParser.loss_of_lock_indicator — Method
loss_of_lock_indicator(; loss_of_lock = false, half_cycle = false, boc_tracking = false) -> Int

The loss-of-lock indicator of an ObsValue, assembled from the bits RINEX 3.05 section 6.7.1 gives it, so that none of them is set by its number:

  • loss_of_lock (bit 0): lock was lost between the previous and this observation, so a cycle slip is possible.
  • half_cycle (bit 1): a half-cycle ambiguity or slip is possible, as it is for a phase tracked before the bit or pilot synchronisation resolved the polarity of the carrier. Software that cannot handle half cycles skips the observation. It holds for this epoch only.
  • boc_tracking (bit 2): an MBOC-modulated signal was tracked as BOC, which may make it noisier.

The indicator, BOC bit included, is defined for carrier phases only (section 6.7.1), so write_epoch! rejects a non-zero one on any other observation.

ObsValue(phase; lli = loss_of_lock_indicator(half_cycle = !polarity_known))

Every character is checked, also for a mixed file. Settled from the constellations a file can carry rather than those seen so far, it does not reject a second constellation that shows up later.

RINEXParser.navigation_times — Method
navigation_times(system; week, transmission_time, toe, toc)
    -> (; week, toc, transmission_time)

The week, toc and transmission_time fields of a navigation record of system - 'G', 'E' or 'C' - from a broadcast message: week and transmission_time are the continuous week and the seconds of week it was broadcast at, and toe and toc its reference times of ephemeris and clock in seconds of week, all on the count of the constellation's own time: the GPS week, the Galileo (GST) week, the BDT week. Splatted into the keywords of an ephemeris:

GPSEphemeris(; prn, ..., navigation_times('G'; week, transmission_time, toe, toc)...)

A message is broadcast within hours of its reference times, but not always in the same week: late on a Saturday the next week's ephemeris is often on the air already with a toe near zero, and just after the rollover the last one of the old week may still be. Each reference time is placed in the week that puts it within half a week of the broadcast, as RTKLIB's adjweek does. The record carries

  • week: the week of toe (Tables A6, A8 and A14), aligned with the GPS week for Galileo - the GST week plus 1024 - and the BDT week for BDS,
  • toc: the calendar time of toc in the week it falls in, in the time system of the constellation - BDT for BDS,
  • transmission_time: the seconds of the record's own week, so a message broadcast in the week before reads negative and one broadcast in the week after reads past the end of the week.
source
RINEXParser.observation_code — Function
observation_code(type::Char, signal) -> String

The RINEX 3.05 observation code of the observable type - 'C' (pseudorange), 'L' (carrier phase), 'D' (Doppler) or 'S' (signal strength) - of a GNSSSignals signal, from the code tables of the constellations (Tables 14, 16 and 19). Available with using GNSSSignals.

observation_code('C', GPSL1CA())    # "C1C"
observation_code('L', BeiDouB1I())  # "L2I", not the "L1I" of RINEX 3.02

The Galileo E1 signals approximated as BOC(1,1) are the same broadcast signal as the CBOC ones, so they share their codes; the BDS-3 signals are named by component, data D and pilot P. A signal RINEX 3.05 has no code for is rejected with an ArgumentError saying why.

source
RINEXParser.observation_codes — Method
observation_codes(signals; types = ('C', 'L', 'D', 'S'))
    -> Vector{Pair{Char,Vector{String}}}

The obs_codes of a RinexObsHeader for the GNSSSignals signals: per satellite system, in order of first appearance, the observation_code of each of types for each of its signals. Available with using GNSSSignals.

observation_codes([GPSL1CA(), GalileoE1B(), GPSL5Q()])
# ['G' => ["C1C", "L1C", "D1C", "S1C", "C5Q", "L5Q", "D5Q", "S5Q"],
#  'E' => ["C1B", "L1B", "D1B", "S1B"]]

RINEXParser.phase_correction — Method
phase_correction(system, code) -> Union{Float64,Nothing}

The correction in cycles that RINEX 3.05 Table A23 gives for the carrier phase code of system, as the satellite issues it, to align it with the reference signal of its band: -0.25 for GPS L2S, 0.5 for Galileo L1C. The sign follows section 5.2.12, φRINEX = φoriginal + Δφ.

The correction is zero for the reference itself and for the signals the table gives no shift ("None").

nothing is a code the table gives no number for: one it says "must be aligned" without saying by how much (GPS L5X, the BDS-3 pilots, ...), one whose correction depends on the satellite (GPS L2C, QZSS L1S), or one it states no alignment for at all (all of SBAS, the restricted GPS Y and M and Galileo A and Z signals, QZSS L1B and L1Z, NavIC L5B and L9B).

See PhaseShift for which codes a header has to state a shift for.

RINEXParser.rinex_ephemeris — Function
rinex_ephemeris(decoder; week = nothing)
    -> Union{Nothing,GPSEphemeris,GalileoEphemeris,BeiDouEphemeris}

The navigation record of a GNSSDecoder GNSSDecoderState, for write_ephemeris!. Available with using GNSSDecoder.

Records exist for GPS LNAV (L1 C/A), Galileo I/NAV (E1-B, E5b) and F/NAV (E5a), and BDS D1/D2 (B1I, B3I). The GPS CNAV and CNAV-2 (L5, L2C, L1C), BDS B-CNAV (B1C, B2a, B2b) and Galileo C/NAV (E6) messages have no RINEX 3.05 record (it arrived with RINEX 4), so those decoders give nothing, as does a message not yet complete for positioning; has_rinex_ephemeris tells the two apart.

week is the continuous week on the constellation's own count (the GPS, GST or BDT week), as PositionVelocityTime.get_week returns it. It defaults to the decoded one for Galileo and BDS; GPS LNAV broadcasts only 10 bits of it, so a GPS decoder needs it given.

The decoded values are converted to the record's units and conventions: issue-of-data and health words, accuracy indices to meters, the fit-interval flag to hours, the Galileo status to galileo_sv_health and galileo_data_sources, and the times by navigation_times. Angles are in radians already and pass through.

RINEXParser.set_header! — Method
set_header!(writer, header) -> writer
set_header!(writer; fields...) -> writer

Replace the header writer - a RinexObsWriter or RinexNavWriter - writes out with its first record, for the fields the data provides late: the corrections and leap seconds decoded from the navigation message, a position solution. header is checked as it is when a writer is created. Once the header is written (see header_written) the file already carries the old one, and an ArgumentError is thrown instead.

RINEXParser.RecordBuffer — Type
RecordBuffer()

Scratch buffer of one data record. Printf writes into a byte buffer without allocating, but its IO method allocates per field, so the data writers assemble each record here and write it in one call. Header records, written once per file, go straight to the IO.

Base.parse — Method
parse(RinexFileName, name) -> RinexFileName
tryparse(RinexFileName, name) -> Union{RinexFileName,Nothing}

Read a RINEX long filename. name may be a path - only its last component is looked at - and its fields may be lower case, although a name that is written out is upper case as the convention prescribes.

A field that is legal but not canonical renders in the convention's unit (24H as 01D, a 60S interval as 01M), so keep the path itself to open the file.

tryparse answers nothing where parse throws an ArgumentError, which selects the file names of a directory that conform to the convention:

filter(!isnothing, tryparse.(RinexFileName, readdir(directory)))

Reading is as strict as the spec. Not read: RINEX 2 short names (algo1600.12o), a one-character compression field (.Z), a zero count in a unit other than U, and a navigation name with a data-frequency field.

RINEXParser.check_observation_code — Method
check_observation_code(system, code) -> code

Return the observation code code, or throw an ArgumentError if RINEX 3.05 does not define it for system. A code is a type, a band and an attribute, and only the combinations of Tables 14-20 are known tracking modes, which section 5.2.17 makes the only ones a file may carry: BDS B1I is 2I rather than 1I, and Galileo E5b and BDS B2b share band 7 under attributes of their own. The one other code the format admits is the receiver channel number X, whose attribute is blank (section 5.3.4).

RINEXParser.period_field — Method
period_field(period) -> String

The file-period field of a long filename, written in the largest of the units minutes, hours, days and years that period is an exact multiple of: Day(1) becomes 01D and Minute(15) becomes 15M. nothing becomes the 00U of a period that is not specified, the field's only zero count.

Every field of eph except the ignored ones, as the key of a record. RINEXParser.reference_code — Method

The reference signal that RINEX 3.05 Table A23 gives the band of the carrier phase code of system.
